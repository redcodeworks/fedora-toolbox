# CLAUDE.md

Guidance for Claude Code in this repo (`redcodeworks/fedora-toolbox`). `AGENTS.md` is Kevin's own file; never create or edit it.

## What this repo is

This repo builds toolbox images only: distrobox/container development environments, each one a top-level directory. octarine-os and any other OS or bootc image live in their own repos and never move here; nothing from them (build files, signature policy, recipes, image names) belongs here. `just new-image` and `just lint` enforce this (a toolbox base in `FROM`, no bootc/ostree/kernel/disk/ISO parts).

The first image is `fedora-toolbox/`, published as `ghcr.io/redcodeworks/fedora-toolbox` (that path is fixed: the host recipe depends on it). It is NOT an OS image: no bootc, ostree, rpm-ostree, kernel, disk or ISO steps. The repo started from the Universal Blue `image-template`; the OS-image parts were removed.

The host (nox, an immutable Fedora Silverblue-based bootc image defined in `redcodeworks/octarine-os`) consumes it through the recipe `ujust toolbox <name>` (the toolbox called `dev` uses this image: `ujust toolbox dev`; the octarine-os repo owns the recipe and the definition `dev.ini`), which creates a distrobox from this image with a SHARED HOME (the box uses the host user's real home). Consequences:
- Nothing user-specific goes into the image: no `/home/<user>` content, no home paths, no dotfiles, no per-user config. `tests/smoke.sh` checks this.
- SDKMAN and nvm are installed at runtime into the shared home by the recipe. They are not part of the image.
- `uv` and `rustup` come from dnf (the `rustup` package; `rustup-init` or the toolchain download happens at runtime in the home).
- The recipe, the host and real `distrobox`/`podman` runs live outside this repo. Anything needing them goes to the hub as `Needs from hub:`.

## Layout (multi-image)

- Every top-level directory that contains a `Containerfile` is one image and its own build context. The image name is the directory name, unless `<dir>/image.env` sets `IMAGE_NAME` (and `IMAGE_DESC`). Directories without a `Containerfile` (`.github`, `tests`, ...) are not images.
- Per image: `<image>/Containerfile` (base, runs `build_files/build.sh`, OCI labels), `<image>/packages/dev.txt` (one package or `@group` per line, `#` comments, one-line diffs), `<image>/build_files/build.sh` (one strict `dnf5 install`; any unavailable package fails the build, no `--skip-unavailable`), `<image>/tests/smoke.sh` (runs inside the built image), optional `<image>/image.env`.
- Shared, at the root: `Justfile`, `README.md`, `CLAUDE.md`, `cosign.pub`, `.github/` (workflows, `.github/scripts/{images,plan-images,lint,new-image}.sh`, `prune-testing.py`, Renovate and Dependabot config), `tests/` (`plan-images.sh`, `new-image.sh`: tests of the shared scripts).
- `fedora-toolbox/` contents: build chain (gcc, g++, gfortran, clang, make, cmake, ninja, meson, gdb, valgrind and friends), common `-devel` libraries (OpenSSL, libpq, GLib, imaging, audio, graphics headers), hardware and ROCm tools, plus `uv`, `rustup` (ships `rustup-init`; `rustup` appears on first run in the home) and `fish` from Fedora. Full list: `fedora-toolbox/packages/dev.txt`.
- Recipes: `just list` (images), `just build <image>`, `just smoke <image>` (by directory or name), `just lint`, `just check` (Justfile format), `just test` (planning, promotion, prune and scaffold tests), `just new-image <name>`, `just release`.
- Add an image: `just new-image <name>` scaffolds `<name>/` (FROM `ghcr.io/ublue-os/fedora-toolbox:latest`, a one-line package list, `build.sh`, a smoke skeleton) and passes `just lint`; edit the list and the smoke test. The name is lowercase letters, digits and dashes and is also the published image name `ghcr.io/redcodeworks/<name>`.

## Image hygiene

The end of each `build.sh` deletes build residue: `/var/log/dnf5.log*` (it contains mirror URLs), `/root/.ssh`, `/root/.viminfo`, `/root/.cache`, `/root/.local/share/wget`, plus the dnf caches. The Containerfile sets its OCI labels explicitly so nothing from the base is republished: `maintainer` (`redcodeworks/fedora-toolbox`, no email), `authors`, `vendor`, `url`, `documentation`, `source`, and `version`, `revision`, `created` from build args (`IMAGE_VERSION` = the dated tag, `IMAGE_REVISION` = the commit sha, `IMAGE_CREATED` = UTC time) that `build-image.yml` passes; local builds get `dev`/`unknown`. The workflow step "Check image labels" fails on any email address in a label or a wrong revision; `tests/smoke.sh` fails on dnf logs or `/root` residue. `just new-image` scaffolds the same cleanup.

## Build once, promote (merge to main)

A merge to `main` PROMOTES the already-tested, already-signed `testing` image to `latest` instead of rebuilding it, when that is provably the same content. Gated by the repository variable `PROMOTE_ENABLED` (must be exactly `true`; Kevin or the hub sets it, never an agent without being told; unset means always build, the previous behaviour).

- Decision per image, in `.github/scripts/promote-decision.sh` (called for every planned image by `plan-promote.sh` in the `plan` job, which adds `mode`, `source` and `reason` to the matrix; tests: `tests/promote-decision.sh`, a temporary git repo and a fake registry lookup). It promotes only for a push to `main` whose HEAD is a merge commit (two parents) where every file differing between HEAD and `HEAD^2` (the testing tip) is docs-only (top-level `*.md`, `docs/**`, `LICENSE`, `.gitignore`), AND walking back the first-parent history of `HEAD^2` (50 commits at most) finds a commit C with a published `testing-<short sha of C>` tag for that image, with every file changed between C and `HEAD^2` docs-only or inside another image's directory (so shared files such as `.github/**` or the same image's directory force a build). It prints `promote <sha7 of C>` or `build <reason>`.
- Always builds: schedule (the weekly build still refreshes `latest`), `workflow_dispatch`, a push to `main` that is not a merge commit, differing trees, no matching testing image, a failed verification, `PROMOTE_ENABLED` not `true`. One image may be promoted while another is rebuilt in the same run.
- Promotion (`build-image.yml`, job `promote`, runs before `build_push`): reads the manifest of `ghcr.io/redcodeworks/<image>:testing-<sha7 of C>`, verifies its digest against `cosign.pub` BEFORE retagging (no signature or a failed verification: warning and fallback to the normal build, nothing is retagged), then `skopeo copy --all --preserve-digests` to `latest` and `latest-<YYYYMMDD>-<sha7 of HEAD>` and asserts that each new tag has the identical manifest digest. `build_push` runs only if nothing was promoted (and not after a failed promote job). The `sign` job takes the promote outputs, skips signing (the signature belongs to the digest and exists from the testing publish) and verifies the digest and every new tag against `cosign.pub`.
- Check names are unchanged: the promote job counts as the build for the aggregate `Build and push image` (a failed or skipped-by-design stage fails or passes the `images` job like before). The plan job has `packages: read` and logs skopeo into ghcr.io for the tag lookups.
- Prune interaction: a promoted version carries `latest*` and `testing*` tags; `prune-testing.py` only considers versions whose tags are ALL `testing*`, so it is never deleted, nor is its signature (`tests/prune-testing.sh`).

## fedora-gaming

A gaming toolbox, published as `ghcr.io/redcodeworks/fedora-gaming` (tags as for every image: `testing*`, `latest*`), modelled on Kevin's Arch `steam-box`, built from the same base. Steam, steam-devices, gamescope, MangoHud (x86_64 and i686), GameMode (x86_64 and i686), vkBasalt, vulkan-tools, mesa-demos, libva-utils, joystick-support, protontricks, winetricks. The list is `fedora-gaming/packages/gaming.txt`; wine, lutris, goverlay and obs-studio-plugin-vkcapture are commented optional lines. Deliberately absent: sunshine, lact, extest, game-devices-udev (not packaged for Fedora 44 in Fedora or RPM Fusion), Decky (out-of-tree installer).

- Package policy: Fedora and RPM Fusion nonfree only (the base enables both; `steam` comes from `rpmfusion-nonfree(-updates)`, there is no separate steam repo on Fedora 44). Terra is dropped on purpose.
- Why Terra goes (facts from a dry run in a throwaway container of the base, 2026-11, Fedora 44): the base ships Terra's Mesa 26.1.0 for x86_64 only and hides Fedora's Mesa with `/etc/dnf/repos.override.d/99-config_manager.repo` (`exclude=mesa-*` on the `fedora*` repos, not on `updates`). `dnf5 install steam gamescope mangohud gamemode` resolves (394 installs) but replaces Terra's Mesa with Fedora `updates` Mesa 26.2.6 for x86_64 and i686; Fedora's is newer and the only source of 32-bit Mesa. So `build.sh` removes the Terra repo files and packages and the exclude override, runs `dnf5 -y distro-sync --refresh 'mesa*'`, then installs the list (with `mesa-vulkan-drivers` listed for both architectures); `mesa-demos` only installs once the exclude is gone.
- Smoke test (`fedora-gaming/tests/smoke.sh`): the gaming packages, `steam` and `gamescope` on PATH, `mesa-vulkan-drivers` x86_64 and i686 at the same version, no Terra package or repo, `libvulkan_radeon` for both architectures, no dnf logs or `/root` residue, nothing user-specific.
- Unverified: gamescope's file capability (`cap_sys_nice`) inside a container; the exact `steam` dependency set beyond what dnf resolves (check the transaction in the CI build log); behaviour on a real host with a GPU. The image expects an isolated home (the host definition is owned by the octarine-os repo) and the `steam-devices` udev rules on the host.

## Package policy

Official Fedora packages only, plus whatever the base already configures (Terra). No COPR, vendor repos or out-of-tree RPMs without Kevin's decision (put it under `Needs from hub:`). Packages already in the base are no-ops. `@group` entries: dnf5 accepts `@id` arguments to `dnf5 install` (mandatory and default members, not optional); the build script passes lines through unchanged, so the form is `@c-development`.

A local build or smoke test creates only a throwaway image/container; if podman is blocked or there is no network (as in the agent sandbox), say plainly that nothing was built. ## Branch, CI and signing rules

- Branch flow (same as `redcodeworks/octarine-os`): `testing` builds and publishes the `testing` image; `main` is protected, changes only by pull request from `testing` (merge commit, never squash or rebase), and publishes `latest`. `just release` opens the pull request from `testing` into `main`; `just release true` also waits for the required checks and merges it (needs `gh`). `.github/workflows/require-testing-branch.yml` fails any pull request into `main` that is not from the `testing` branch of this repository. Required checks on `main` (as on octarine-os, applied 2026-11-07): `Build and push image`, `require-testing-branch` and `Sign and verify images`; pull request required (0 approvals), admins enforced, merge commits only. Never push, open pull requests or merge unless Kevin asked.
- CI picks images per run (`.github/workflows/build.yml`, no workflow-level `paths:` filter, which would leave required checks pending forever). The `plan` job runs `just check`, `just lint`, the two test scripts and `.github/scripts/plan-images.sh`, which prints the matrix: pull requests and pushes build the images whose directory has changed files in the commit range (PR base to head, `github.event.before` to `github.sha`); a change to a shared file (anything under `.github/` except `renovate.json5` and `dependabot.yml`, the root `Justfile`, `cosign.pub`) builds all images; an all-zero or unknown before-SHA builds all; the weekly schedule (exactly one cron entry, `0 6 * * 0`, Sunday 06:00 UTC, runs on the default branch) builds all; `workflow_dispatch` builds all or the one named in its optional `image` input; nothing changed gives an empty matrix. Each planned image runs the reusable `build-image.yml` (podman build with the image directory as context, `<image>/tests/smoke.sh`, publish, then the separate `sign` job; concurrency per image).
- Concurrency: a newer push to `testing` (or a pull request update) cancels the older pending or running build of the same ref; runs on `main` and the weekly schedule are never cancelled. A cancelled run fails (never passes) the aggregate checks, but a cancel after publish and before `sign` can leave the `testing` tags unsigned until the next build finishes; the next push plans only its own commit range, so an image changed only by a cancelled commit is not rebuilt by it (the pull request build and the build on `main` cover it).
- One build per commit: a pull request from this repo's `testing` branch does not build. Its `mirror` job (build.yml) waits for the push run of the same head SHA (up to 40 minutes, fails if no push run shows up within 3 minutes) and the aggregate jobs `Build and push image` and `Sign and verify images` take that run's result; `plan` and `images` are skipped. Pull requests from anywhere else (Renovate, forks) keep the full plan and build. Consequence: the PR no longer re-plans the whole base-to-head range, so an image changed only by a commit whose push build was cancelled is first built by the merge to `main`. Re-running a failed push build needs a re-run of the PR run too. Runners are pinned to `ubuntu-26.04` everywhere (no `ubuntu-latest`, so a runner image change is a commit). The cosign install is the composite action `.github/actions/install-cosign` (one place for the version). Registry layer caching was evaluated and rejected: each image is the base plus one `dnf5 install` layer, a cache hit would reuse a stale package set on the weekly rebuild, and a changed package list always invalidates that layer.
- Tags per image (`ghcr.io/redcodeworks/<name>`): pushes to `testing` publish `testing`, `testing-<short sha>` (the promote lookup key) and `testing-<YYYYMMDD>-<short sha>`; pushes to `main`, the weekly schedule and manual runs on `main` publish `latest` and `latest-<YYYYMMDD>-<short sha>`. Pull requests build and smoke-test only: no push, no signing. The `sign` job (environment `signing`) signs every distinct pushed digest and verifies each digest and tag against `cosign.pub`.
- Required check names (unchanged by the multi-image layout): the aggregate jobs `Build and push image` and `Sign and verify images` in `build.yml` (each passes when every planned image succeeded or the plan was empty; signing runs inside the per-image workflow, so a failure anywhere fails both) and `require-testing-branch`. Per-image jobs are shown as `images (<name>) / Build image` and `images (<name>) / Sign and verify image` and are not required.
- Pruning: `.github/workflows/prune-testing.yml` with `.github/scripts/prune-testing.py` runs Sundays 04:17 UTC once per image (a matrix over the image directories, names by the same rules). For each image it keeps the newest 10 `testing` builds and deletes older ones with their cosign `.sig` versions; it never touches anything tagged `latest*` or any version with a non-`testing` tag, deletes untagged versions older than 7 days, and refuses to delete more than 60 versions per run. Scheduled runs only delete when the repository variable `PRUNE_ENABLED` is `true`, otherwise they are dry runs; a manual run defaults to dry run.
- Signing: public key `cosign.pub` is committed at the repo root. The private key is the secret `SIGNING_SECRET` stored in the GitHub environment `signing` (not at repo level, environment limited to `main` and `testing`); only the `sign` job uses that environment, so the build job never sees the key. `cosign.key` is gitignored and must never be read, printed or committed. Old bundle format (`--new-bundle-format=false --use-signing-config=false`). One-time setup (done 2026-11-07): `COSIGN_PASSWORD="" cosign generate-key-pair` (unprotected key, CI cannot use a passphrase), commit `cosign.pub`, store `cosign.key` as the environment secret `SIGNING_SECRET`, enable GitHub Actions. A new image's ghcr package is private after its first publish: Kevin sets it public in the web UI (not possible via API) so distrobox can pull it without login.
- Renovate and branch protection: automerge of base-digest bumps only works if protection on `main` lets it through; Renovate's own branches fail `require-testing-branch`, so those digest PRs need a manual merge or a ruleset exception (assumption, unverified until a Renovate PR exists; the Renovate app must be installed).
- Base digest pinning: Renovate (`config:best-practices`, Containerfile manager matching every `*/Containerfile`) pins the `FROM` digest of `ghcr.io/ublue-os/**` bases and opens update PRs; digest bumps of the base automerge. Actions are pinned by SHA and updated by Renovate and Dependabot.
- Commits: on `testing`, explicit paths only (never `git add -A`), message says why, trailer `Co-Authored-By` from the session reminder.
