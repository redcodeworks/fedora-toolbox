## What this repo is

Charter (Kevin, 2026-11-16): `octarine-bins` (`~/Repos/octarine-bins`) holds every BUILD-TIME dependency of the octarine-os images (binaries and package lists, signed images pinned by digest); this repo, `octarine-images`, holds the DISTROBOX images only: `fedora-toolbox`, `fedora-gaming`, `dna-toolbox`, and `datastore-images` until it becomes a distrobox container (design pending; its directory is not touched by the cleanup). Runtime images stay FLOATING (unpinned) for now. One sentence per box: `fedora-toolbox` is the octarine-os dx developer tools in a distrobox, `fedora-gaming` is the octarine-os gx gaming packages (minus Sunshine) in a distrobox on Fedora's Mesa, `dna-toolbox` is the data, analytics and AI box with its own two package lists. octarine-os and any other OS or bootc image live in their own repos and never move here; nothing from them (build files, signature policy, recipes) belongs here. `just new-image` and `just lint` enforce this (a toolbox base in `FROM`, no bootc/ostree/kernel/disk/ISO parts).

`fedora-toolbox` is published as `ghcr.io/redcodeworks/fedora-toolbox` (that path is fixed: the host recipe depends on it). None of the boxes is an OS image: no bootc, ostree, rpm-ostree, kernel, disk or ISO steps. The repo started from the Universal Blue `image-template`; the OS-image parts were removed.

The host (nox, an immutable Fedora Silverblue-based bootc image defined in `redcodeworks/octarine-os`) consumes the boxes through the recipe `ujust toolbox <name>` (the toolbox called `dev` uses `fedora-toolbox`: `ujust toolbox dev`; the octarine-os repo owns the recipe and the definition `dev.ini`), which creates a distrobox from the image with a SHARED HOME (the box uses the host user's real home). Consequences:
- Nothing user-specific goes into the image: no `/home/<user>` content, no home paths, no dotfiles, no per-user config. `tests/smoke.sh` checks this.
- SDKMAN and nvm are installed at runtime into the shared home by the recipe. They are not part of the image.
- `uv` and `rustup` come from dnf (the `rustup` package; `rustup-init` or the toolchain download happens at runtime in the home).
- The recipe, the host and real `distrobox`/`podman` runs live outside this repo. Anything needing them goes to the hub as `Needs from hub:`.

## Layout (multi-image)

- Every top-level directory that contains a `Containerfile` is one image and its own build context (the dna-stack build contexts are NOT top-level, so they are not images). The image name is the directory name, unless `<dir>/image.env` sets `IMAGE_NAME` (and `IMAGE_DESC`). Directories without a `Containerfile` (`.github`, `tests`, ...) are not images.
- Per image: `<image>/Containerfile` (base, runs `build_files/build.sh`, OCI labels), `<image>/packages/*.txt` (one package or `@group` per line, `#` comments, one-line diffs; only `dna-toolbox` has lists of its own, `required-fedora.txt` and `optional-fedora.txt` in the octarine-bins naming; `fedora-toolbox` and `fedora-gaming` take theirs from a pinned octarine-bins image, see "Package lists and installer from octarine-bins"; the scaffold of `just new-image` still writes `packages/dev.txt`), `<image>/build_files/build.sh` (one strict `dnf5 install`; any unavailable package fails the build, no `--skip-unavailable`), `<image>/tests/smoke.sh` (runs inside the built image), optional `<image>/image.env` (`IMAGE_NAME`, `IMAGE_DESC`, and since 2026-11-09 `IMAGE_KIND=list` for a data image (only `datastore-images`), `IMAGE_SCHEDULE=false` to leave an image out of the weekly schedule, `BUILD_CONTEXT=.` for the repository root as build context (only datastore-images uses it since 2026-11-16), `DATA_FILES="<repo path>:<image path> ..."` for a list image (the build compares the image's files with these; a directory stands for its files), `DATA_CHECK=<repo script>` (run on the files extracted from the built image), `EXTRA_PATHS=<dirs>` for other top-level directories whose changes rebuild this image and never count as another image's directory in the promote decision).
- Shared, at the root: `Justfile`, `README.md`, `CLAUDE.md`, `cosign.pub`, `.github/` (workflows, `.github/scripts/{images,plan-images,lint,new-image}.sh`, Renovate and Dependabot config), `tests/` (`plan-images.sh`, `new-image.sh`: tests of the shared scripts).
- `fedora-toolbox/` contents: build chain (gcc, g++, gfortran, clang, make, cmake, ninja, meson, gdb, valgrind and friends), common `-devel` libraries (OpenSSL, libpq, GLib, imaging, audio, graphics headers), hardware and ROCm tools, plus `uv`, `rustup` (ships `rustup-init`; `rustup` appears on first run in the home) and `fish` from Fedora. The list is the dx list of the pinned `octarine-bins-dx` image minus the VM-hosting set (see "Package lists and installer from octarine-bins"); `build.sh` runs that image's `/packages/install.sh` with `EXCLUDE`.
- Recipes: `just list` (images), `just build <image>`, `just smoke <image>` (by directory or name), `just lint`, `just check` (Justfile format), `just test` (planning, promotion and scaffold tests), `just new-image <name>`, `just release`.
- Add an image: `just new-image <name>` scaffolds `<name>/` (FROM `ghcr.io/ublue-os/fedora-toolbox:latest`, a one-line package list, `build.sh`, a smoke skeleton) and passes `just lint`; edit the list and the smoke test. The name is lowercase letters, digits and dashes and is also the published image name `ghcr.io/redcodeworks/<name>`.

## Image hygiene

The end of each `build.sh` deletes build residue: `/var/log/dnf5.log*` (it contains mirror URLs), `/root/.ssh`, `/root/.viminfo`, `/root/.cache`, `/root/.local/share/wget`, plus the dnf caches. The Containerfile sets its OCI labels explicitly so nothing from the base is republished: `maintainer` (`redcodeworks/octarine-images`, no email), `authors`, `vendor`, `url`, `documentation`, `source`, and `version`, `revision`, `created` from build args (`IMAGE_VERSION` = the dated tag, `IMAGE_REVISION` = the commit sha, `IMAGE_CREATED` = UTC time) that `build-image.yml` passes; local builds get `dev`/`unknown`. The workflow step "Check image labels" fails on any email address in a label or a wrong revision; `tests/smoke.sh` fails on dnf logs or `/root` residue. `just new-image` scaffolds the same cleanup.

## Build once, promote (merge to main)

A merge to `main` (a promotion PR from `testing`) PROMOTES the already-tested, already-signed `testing` image to `latest` instead of rebuilding it, when that is provably the same content. Gated by the repository variable `PROMOTE_ENABLED` (must be exactly `true`; Kevin or the hub sets it, never an agent without being told; unset means always build, the previous behaviour).

- Decision per image, in `.github/scripts/promote-decision.sh` (called for every planned image by `plan-promote.sh` in the `plan` job, which adds `mode`, `source` and `reason` to the matrix; tests: `tests/promote-decision.sh`, a temporary git repo and a fake registry lookup). It promotes only for a push to `main` whose HEAD is a merge commit (two parents) where every file differing between HEAD and `HEAD^2` (the testing tip) is docs-only (top-level `*.md`, `docs/**`, `LICENSE`, `.gitignore`), AND walking back the first-parent history of `HEAD^2` (50 commits at most) finds a commit C with a published `testing-<short sha of C>` tag for that image, with every file changed between C and `HEAD^2` docs-only or inside another image's directory (so shared files such as `.github/**` or the same image's directory force a build). It prints `promote <sha7 of C>` or `build <reason>`.
- Always builds: schedule (the weekly build still refreshes `latest`), `workflow_dispatch`, a push to `main` that is not a merge commit, differing trees, no matching testing image, a failed verification, `PROMOTE_ENABLED` not `true`. One image may be promoted while another is rebuilt in the same run.
- Promotion (`build-image.yml`, job `promote`, runs before `build_push`): reads the manifest of `ghcr.io/redcodeworks/<image>:testing-<sha7 of C>`, verifies its digest against `cosign.pub` BEFORE retagging (no signature or a failed verification: warning and fallback to the normal build, nothing is retagged), then `skopeo copy --all --preserve-digests` to `latest` and `latest-<YYYYMMDD>-<sha7 of HEAD>` and asserts that each new tag has the identical manifest digest. `build_push` runs only if nothing was promoted (and not after a failed promote job). The `sign` job takes the promote outputs, skips signing (the signature belongs to the digest and exists from the testing publish) and verifies the digest and every new tag against `cosign.pub`.
- Check names are unchanged: the promote job counts as the build for the aggregate `Build and push image` (a failed or skipped-by-design stage fails or passes the `images` job like before). The plan job has `packages: read` and logs skopeo into ghcr.io for the tag lookups.

## Package lists and installer from octarine-bins (stage 3, 2026-11-16)

The toolbox builds no longer carry package lists or an installer of their own for the OS variants: `dev-packages/`, `gaming-packages/`, `package-installer/` and their CI jobs, tests and lint rules were retired on 2026-11-16 (the lists moved to the `octarine-bins-dx` and `octarine-bins-gx` images of `~/Repos/octarine-bins`, which owns their lint and list tests; the old published packages `ghcr.io/redcodeworks/{dev,gaming,dna}-packages` stay in the registry, Kevin deletes them by hand, and octarine-os pins them by digest until its own stage 2 merges: never unpublish them). One sentence: a box takes its lists and the installer from the bins image of its variant, PINNED by digest and verified with the octarine-bins public key, and adds nothing but a few box-specific exclusions.

- Pins: `fedora-toolbox` and `dna-toolbox` pin `ghcr.io/redcodeworks/octarine-bins-dx`, `fedora-gaming` pins `octarine-bins-gx`, each in its own Containerfile as `ARG BINS_TAG=<YYYYMMDD>-<sha7>` (the image's version label, for humans), `ARG BINS_DIGEST=sha256:...` and `FROM ghcr.io/redcodeworks/octarine-bins-<dx|gx>@${BINS_DIGEST} AS bins` (same pattern as the octarine-bins pin in octarine-os). `just lint` checks the shape. The first pins (2026-11-16) are the `latest` of both images at 20261117-5d8004e: dx `sha256:4ca94a16...`, gx `sha256:b42ec749...` (read with `skopeo inspect --raw | sha256sum`).
- Verification: `keys/octarine-bins.pub` is a copy of the `cosign.pub` of octarine-bins (committed here like octarine-os does with its `keys/octarine-bins.pub`; a changed copy means the bins repo rotated its key, take it from `git -C ~/Repos/octarine-bins show origin/main:cosign.pub`). The step "Verify the pinned octarine-bins image" of `build-image.yml` (`bins-pins.sh verify <dir>`, before the build; no-op for an image without a bins pin) runs `cosign verify --key keys/octarine-bins.pub <image>@<digest>`. `keys/` counts as a shared file in the plan (a change builds every image).
- Bump path (chosen: a recipe, not a weekly workflow): `just bump-bins dx|gx` (`.github/scripts/bins-pins.sh bump`, tested by `tests/bins-pins.sh` with stub skopeo and cosign) resolves `latest`, verifies the digest, reads the version label and rewrites tag and digest in every Containerfile that pins that image (dx: fedora-toolbox and dna-toolbox, gx: fedora-gaming); nothing is written when the digest or signature fails. Run it on a `feat/bump-bins-<kind>` branch, one PR per pin. A weekly workflow like octarine-os's `bump-pins.yml` would need `bump-run.sh`/`bump-weekly.sh` machinery (about 150 lines of PR, branch and table logic) or the repository setting that lets Actions create pull requests; not worth it for two pins that move when Kevin decides. Renovate does not touch these pins (its Containerfile rules cover `ghcr.io/ublue-os/**` only).
- How a box installs: the Containerfile bind-mounts the pinned image's `/packages` (the lists and `install.sh`) into the build step. `/packages/install.sh` runs `required-fedora`, `required-negativo17`, `required-copr` (strict: any unavailable package fails the build), then `optional-fedora`, `optional-negativo17`, `optional-copr` (best effort: retried as a whole, then package by package; a package that cannot be installed is printed as `OPTIONAL PACKAGE MISSING` and goes to `$MISSING_FILE`), skipping lists the image does not carry. Environment: `MISSING_FILE`, `EXCLUDE="a b"` (entries dropped, even an alternative or `@group`, not looked up), `ENABLE_REPO`, `NO_CLEANUP=1`, `PACKAGES_DIR`. Full contract: `git -C ~/Repos/octarine-bins show origin/main:CLAUDE.md`, "The package lists". The copr lists need `dnf5-plugins` in the box; the negativo17 lists need the `fedora-multimedia` repository defined (disabled; the installer enables it for that call). The ublue toolbox base has no negativo17 repo, so `fedora-gaming` writes the definition itself.
- `fedora-toolbox`: runs the dx lists unchanged except `EXCLUDE` of the VM-hosting set (libvirt, qemu-kvm, cockpit-machines, virt-install, virtiofsd, swtpm, dnsmasq, edk2-ovmf and the virtualization extras of the optional list) in `build_files/build.sh`: those are for the dx OS image, not for a development box. Everything else of dx (toolchain, `-devel` libraries, `uv`, `rustup`, `fish`, tracing and hardware tools) is installed, so the box and the dx image cannot drift. Fedora 44 base versus the Fedora 45 lists: the strict list must resolve on 44 (alternatives such as `libgit2_1.9-devel|libgit2-devel` cover renames); only CI proves it.
- `fedora-gaming`: Terra removal and the Mesa distro-sync stay (the base's own choice, see the fedora-gaming section), then the box writes the disabled `fedora-multimedia` repository and runs the gx installer ONCE on a copy of the lists without `required-copr.txt` (Sunshine is the OS image's streaming host, deliberately not in the box): required-fedora, required-negativo17 (Steam), optional-fedora.
- `dna-toolbox`: its two lists are now `dna-toolbox/packages/required-fedora.txt` (was core) and `optional-fedora.txt` (was optional) in the bins naming, and the box runs the dx installer (bind-mounted at `/installer`, the same dx pin as fedora-toolbox) with `PACKAGES_DIR=/ctx/packages`. The separate `dna-packages` image had no consumer besides `dna-toolbox` (checked in this repo and in octarine-os and octarine-bins on 2026-11-16) and was retired. Behavior change: the optional tier is one transaction with a whole-group retry and then package by package (was one package at a time).
- Build contexts are the image directories again (no `BUILD_CONTEXT=.`, no `EXTRA_PATHS`, no `Containerfile.dockerignore` for these three); a pin bump changes the image's own Containerfile, so only that image rebuilds.

## Build provenance attestation (second signal, 2026-11-17; the key signature stays the gate)

Job `attest` ("Attest build provenance") of `build-image.yml`, one per image because the reusable workflow runs once per image: `needs: [build_push, sign]`, runs only when `sign` succeeded and `build_push` published (`publish == 'true'`), logs in to ghcr and runs `actions/attest` (pinned by SHA like octarine-bins) with `subject-name` = the image, `subject-digest` = the one digest `push-tags.sh` pushed, `push-to-registry: true`, `create-storage-record: false`. Permissions: contents read, packages write, id-token write, attestations write; no environment, key, checkout or cache. The `sign` job, which holds `SIGNING_SECRET`, has NO `id-token` and NO `attestations`. It lives in the reusable workflow because the digest is only an output of `build_push` there (a matrix caller job's outputs are last-write-wins); the cost is that the `images` job of `build.yml` must grant `id-token: write` and `attestations: write` (a called workflow's permissions are capped by the caller). A promote run attests nothing: it retags the digest testing built, so the attestation carries over. Not a required check: re-run with `gh run rerun --failed`. For a reusable workflow the signer identity is `build-image.yml` (not `build.yml`), the source ref is the caller's ref. A reader checks an image, pinned to its digest (`<image>` is fedora-toolbox, fedora-gaming, dna-toolbox, datastore or datastore-images):

```
gh attestation verify oci://ghcr.io/redcodeworks/<image>@<digest> \
  --repo redcodeworks/octarine-images \
  --signer-workflow redcodeworks/octarine-images/.github/workflows/build-image.yml \
  --source-ref refs/heads/testing   # refs/heads/main for an image built on main (weekly schedule, fallback build)
```

Images published before 2026-11-17 have no attestation. Not testable locally (needs GitHub OIDC and Sigstore): the first real build on `testing` is the proof.

## datastore-images (2026-11-15): the lakehouse datastore bundle

Kevin's decision (2026-11-15, "keep services as Quadlets"): the opt-in datastore (PostgreSQL, Valkey, SeaweedFS in the `datastore` pod, Kafka in the `kafka` pod, rootless Podman Quadlets) is an ON-DEMAND BUNDLE published from here, no longer baked into the octarine-os dx image. The signed image `ghcr.io/redcodeworks/datastore-images` (FROM scratch, same name, same publish, signing pipeline as before) carries the whole bundle; the dx image only keeps a thin recipe that pulls, verifies and extracts it (briefed to image-project by the hub). Nobody bumps the pins automatically.

- Layout (repo = extracted image, so `bin/datastore` runs from a checkout and from the extracted image alike; it finds the rest in the directory above `bin/`): `images.txt` (hand-maintained pins, `<name> <image>:<tag>@sha256:<digest>`, names postgresql valkey seaweedfs kafka, validated by `validate.sh`), `quadlets/` (the 11 templates, `@<NAME>_IMAGE@` placeholders; the files are byte-identical to what octarine-os rendered, only the install location differs), `lib/render.sh` (fills the placeholders from images.txt; parses, never sources; refuses a bad line, a missing or duplicate image, a leftover placeholder), `lib/datastore.sh` (helpers and `ds_validate`), `bin/datastore` (the command), `README.md` (image `/README`). Not in the image: `validate.sh`, `check-bundle.sh`, `image.env`, `Containerfile*`. Image paths: `/images.txt /README /bin/datastore /lib/*.sh /quadlets/*`.
- Command: `datastore install [--no] [--force] | uninstall [--no] | render DIR | start|stop [datastore|kafka|all] | status | logs SERVICE | setup [--yes|--no] [--status] [--pin S=TAG] [--unpin S] [--update] [--backup DIR [--stop]] | --help`. It is the old `ujust datastore` (start/stop/status/logs) and `ujust datastore-setup` (now `datastore setup`) with their behavior and messages unchanged; `DATASTORE_UJUST=1` makes the messages name the ujust recipes (`ujust datastore ...`, `ujust datastore-setup ...`). Only bash, coreutils, sed, awk, podman, systemctl; the tests run it on a PATH that holds just those. Refuses root; `--help`, `render` and `install --no` need no podman. Unlike the old recipes there is no `menu.sh` dependency: confirmations are a plain `read` on a terminal and "no" without one.
- Install target is the USER Quadlet directory (`$DATASTORE_USER_DIR`, default `${XDG_CONFIG_HOME:-$HOME/.config}/containers/systemd`): render into a staging directory next to it (`.datastore-stage.*`, removed on exit), `ds_validate` (no `[Install]` section; every `<service>.container` with ContainerName pgsql/valkey/seaweedfs/kafka and exactly one Image= equal to the images.txt reference; `<volume>.volume` with `VolumeName=` postgresql-data valkey-data seaweed-data kafka-data; `PodName=datastore`/`kafka`; `NetworkName=lakehouse`: the names existing users' data and secrets depend on), then each file is copied to `<name>.tmp-<pid>` (a name Quadlet ignores) and renamed (atomic per file). Idempotent: an identical file is left alone (same inode). A record `${XDG_STATE_HOME:-~/.local/state}/datastore/installed` (`<sha256>  <name>` lines) says what was installed: a differing file that is not in the record, or whose hash no longer matches it (user edit), is refused unless `--force`; a recorded file that left the bundle is removed when unchanged. Runs `systemctl --user daemon-reload`, never starts anything, creates no volume or secret. `uninstall` removes only recorded, unchanged files, refuses while a pod is active, keeps drop-ins (pins) and foreign units, never removes volumes or secrets and prints the `podman volume rm` / `podman secret rm` commands to run on purpose. `setup --status` shows `bundle <ref> (differs: ...)` when the installed units are older than the bundle's images.txt (run `install` again). Pin, update and start need the units installed (message names `datastore install`).
- Quadlet precedence, VERIFIED here (podman 6.1.3 generator, `/usr/libexec/podman/quadlet --user --dryrun`, temp HOME): for a unit name in two search directories the first directory of the search path wins and the other file is not even loaded (one service generated); the user directory (`$XDG_CONFIG_HOME/containers/systemd`) comes before `/usr/share/containers/systemd/users` (podman-systemd.unit(5), "Podman rootless unit search path"; the man page and `QUADLET_UNIT_DIRS` order agree). So while an older image still ships the same names under `/usr/share/containers/systemd/users`, the user's installed copies take precedence (`install` prints a note when `/usr/share/containers/systemd/users/datastore.pod` exists). Drop-ins (`<unit>.container.d`) merge by unit name across directories. The tests guard this when the generator is installed (skipped otherwise).
- Tests: `tests/datastore-bundle.sh` (ported from octarine-os `tests/datastore.sh`, plus install/uninstall; run by `just test`; no literal image references, they are read from images.txt; the postgresql pins used in the pin tests are derived from its tag) and `tests/datastore-images.sh` (validator, discovery, planning, Containerfile shape).
- CI: a normal matrix image, built when `datastore-images/` or a shared file changes (every bundle file lives under the directory, so any change rebuilds and publishes; nothing else builds it); `testing*` tags from `testing`, `latest*` from `main` (promote-by-tree-hash applies), cosign-signed, not in the weekly schedule. The step "Check data image contents" compares every `DATA_FILES` file (a directory entry such as `datastore-images/bin:bin` expands to its files, see `images.sh data-files`) with the repository, including the executable bit, then runs `DATA_CHECK` (`datastore-images/check-bundle.sh`, via `images.sh data-check`) on the files extracted from the BUILT image: `--help`, `render` equals the repository's render, `install` into a temporary HOME with a stub systemctl (idempotent), `uninstall`. Like every new package it is private after the first publish: Kevin sets it public (it already is).
- Consumer contract (the thin recipe, in the image's README): `podman pull <ref>`, `podman create <ref> /images.txt`, `podman export <cid> | tar -x -C <dir>`, `podman rm <cid>`, then `<dir>/bin/datastore`. Signature: podman verifies it itself when `/etc/containers/policy.json` has a `sigstoreSigned` entry for `docker: ghcr.io/redcodeworks/datastore-images` with `keyPath` = this repo's `cosign.pub` and `signedIdentity: matchRepository`, AND a `registries.d` file with `use-sigstore-attachments: true` for that path (VERIFIED with skopeo and podman on the published testing image: good key accepted, wrong key rejected, missing registries.d entry rejected with "a signature was required, but no signature exists"); no cosign binary is needed, `cosign verify --key cosign.pub <ref>@sha256:<digest>` is the alternative and also passes. A user-level `$HOME/.config/containers/policy.json` REPLACES the system one (not merged), so prefer the system files or `podman pull --signature-policy FILE` (registries.d has no flag, skopeo has `--registries.d DIR`).
- Unverified until a main run: promotion of `testing` to `latest` for this image (the promote decision is generic); everything on `testing` is checked by its CI run.

## datastore (the box, 2026-11-16)

Kevin's decision (2026-11-16): the datastore becomes ONE distrobox, `ghcr.io/redcodeworks/datastore` (directory `datastore/`). Model: one box with its own systemd running Postgres, Valkey, SeaweedFS and Kafka as ordinary units, on the `lakehouse` network under the aliases of today's Quadlets, data in plain directories under the shared home (`$HOME/.local/share/datastore/{postgres,valkey,seaweed,kafka}`), local development only. `datastore-images/` (the Quadlet bundle) is untouched and keeps working until Kevin cuts over.

- Built image (FROM `registry.fedoraproject.org/fedora:45`, floating): `packages/required-fedora.txt` (PostgreSQL 17 `postgresql17-server` 17.9, the live data's major; `postgresql-server` 18 conflicts with it; Valkey; `java-25-openjdk-headless`, Fedora 45 has no java-21; `glibc-langpack-en` because the postgres image used en_US.utf8; systemd and the packages distrobox would install at first start), then `downloads.lock` (`name|version|url|algorithm|checksum`: SeaweedFS 4.53 from GitHub releases sha256, Kafka 4.3.2 from archive.apache.org sha512; `build.sh` verifies and fails on a mismatch; `/usr/local/bin/weed`, `/opt/kafka`). No cache mount in the Containerfile (it broke dnf's package cache in a local build). The image carries `/usr/bin/datastore` and `/usr/share/datastore/units/*.service.in`.
- Units are rendered by `datastore setup` with the box user's name (`User=@USER@`, `@DATA@`, `@CONF@`) into `/etc/systemd/system` through sudo (distrobox gives the user passwordless sudo) and enabled, so they start with the box. Postgres has `RuntimeDirectory=postgresql` (`/run/postgresql` is gone after a box restart), `-c listen_addresses=* wal_level=logical max_replication_slots=10 max_wal_senders=10`, initdb with `-U postgres`, scram for socket and host, `host all all 0.0.0.0/0 scram-sha-256` appended to pg_hba.conf. ## Architecture: x86_64 only (Kevin, 2026-11-09)

Apple Silicon and other architectures are NOT supported for now (a roadmap item in the hub, not in the README). Reasons: the three images and their base `ghcr.io/ublue-os/fedora-toolbox` are single-architecture x86_64 manifests, CI has no arm64 build, Fedora's ROCm packages and the NVIDIA CUDA repository path used by `dna-gpu` are x86_64, ROCm and CUDA do not support Apple GPUs, and distrobox runs only on Linux. Behavior: `dna-gpu rocm|cuda` check `uname -m` first (no rpm or dnf call) and stop with exit 1 and an explanation before any repo or install step; the NVIDIA URL is never built from `uname -m` to try other architectures; `status` prints the architecture and `help` works. `dna-doctor` and `dna-setup` print the architecture and a one-line notice when it is not x86_64. Known limitation (unverified): under qemu-user emulation `uname -m` inside the box reports x86_64 even on an ARM host, so the check cannot catch emulation and no detection is attempted. A future arm64 effort needs: a CI matrix on arm64 runners plus a multi-arch manifest per image, a multi-arch check of the pulled stack images (postgres, seaweedfs, lakekeeper, trino, kafka) and of the Connect, Airflow and Superset base digests (pin manifest lists, which they already are, and confirm an arm64 entry), and an architecture-aware `dna-gpu`.

## Branching and CI (GitLab Flow, Kevin's standard since 2026-11-13)

- Lanes. Dev (`feat/<topic>`, `fix/<topic>`, `hotfix/<topic>`, pushed with full refs `refs/heads/...`): the test lane, `.github/workflows/test.yml` runs on every push to a branch except `main` and `testing` and on pull requests into `testing`; jobs `test` (`just check`, `just lint`, `just test` on the hosted runner, no image build, nothing published) `secrets` (gitleaks over the full history, pinned) and `zizmor` (workflow audit of `.github`, pinned release; NOT a required check; findings are fixed or get a narrow documented per-file ignore in `.github/zizmor.yml`). A weekly cron (Wednesdays 06:00 UTC) runs only `zizmor` (`test` and `secrets` skip on `schedule`); the cron only proves itself on `main`. `testing`: the build lane, `build.yml` builds, smoke-tests, publishes and signs the `testing*` images on every push (a merge). `main`: the promote lane, a merge promotes the tested `testing` image to `latest*` without a rebuild when the content is provably identical (next section) and builds only otherwise.
- Who merges what: the agent opens a PR from the dev branch into `testing` and squash-merges it itself once `test` and `secrets` are green and no build on `testing` is running (a newer merge cancels an older pending build), then opens or amends the single promotion PR `testing` into `main` right away (title and body: what it carries and what is verified, no build-state text). Kevin alone approves and merges the promotion PR (merge commit, never squash or rebase). Nobody commits straight on `testing` or `main`. `just release` still opens the promotion PR by hand. Rulesets and repo settings are the hub's (agents report names, never change them).
- Required checks (rulesets applied by the hub): `testing` requires `test` and `secrets`; `main` requires `Build and push image`, `require-testing-branch` and `Sign and verify images`. A pull request from `testing` runs no build of its own: the checks come from the push run of the same commit on `testing`, reported on the same SHA (`build.yml` has no `pull_request` trigger and no mirror job; `require-testing-branch.yml` is the only pull-request workflow into `main`). The names are an API: the `test` job must never be named like a required check of another stage.
- `tests/workflow-triggers.sh` asserts the triggers and check names above; `tests/push-tags.sh` the single push.
- Merge methods and branch cleanup (hub settings): squash and merge commits on, rebase off, auto-delete merged branches. Never rebase or squash `testing` into `main`.
- Planning: `.github/scripts/plan-images.sh` (no workflow-level `paths:` filter, which would leave required checks pending forever) picks images per run: pushes build the images whose directory (or `EXTRA_PATHS` directories, unused by the three boxes since 2026-11-16) has changed files between `github.event.before` and `github.sha`; a change to a shared file (anything under `.github/` except `renovate.json5` and `dependabot.yml`, the root `Justfile`, `cosign.pub`, anything under `keys/`) builds all images; an all-zero or unknown before-SHA builds all; the weekly schedule (exactly one cron entry, `0 6 * * 0`, Sunday 06:00 UTC, runs on the default branch) builds all images except those with `IMAGE_SCHEDULE=false` (datastore-images); `workflow_dispatch` builds all or the one named in its optional `image` input (from a branch other than `main` or `testing` it builds and smoke-tests only); nothing changed gives an empty matrix. The lint and tests are not repeated in the plan job (they are the test lane). Each planned image runs the reusable `build-image.yml` (podman build with the image directory (or `BUILD_CONTEXT`) as context, `<image>/tests/smoke.sh` (a data image gets a contents check instead), publish, then the separate `sign` job; concurrency per image).
- Concurrency: a newer push to `testing` cancels the older pending or running build of the same ref; runs on `main` and the weekly schedule are never cancelled. A cancelled run fails (never passes) the aggregate checks, but a cancel after publish and before `sign` can leave the `testing` tags unsigned until the next build finishes; the next push plans only its own commit range, so an image changed only by a cancelled commit is not rebuilt by it; the promote decision then sees that commit's changes and builds on `main`.
- Runners are pinned to `ubuntu-26.04` everywhere (no `ubuntu-latest`). `cosign` and `just` are installed by the composite action `.github/actions/setup-tool` (input `tool`; one place for the pinned versions: cosign v3.1.4, just 1.59.0): a step resolves the version, cache dir and key; `actions/cache` (pinned by SHA) restores it; a hit is used only if the binary runs; on a miss the pinned installer runs with `continue-on-error`, a failure prints a `::warning::`, waits 60 s and runs a second attempt that fails the job if it fails too (a GitHub release download once returned a 504 and left `latest` unpromoted). Cosign is cached everywhere except the `sign` job: it passes `cache: "false"` (default `true`), so where the signing key is present a restored executable never runs and the pinned installer downloads and verifies cosign fresh. A run reads the caches of its own branch and the default branch and writes only its own. Registry layer caching was evaluated and rejected (a hit would reuse a stale package set on the weekly rebuild).
- Tags per image (`ghcr.io/redcodeworks/<name>`): pushes to `testing` publish `testing`, `testing-<short sha>` (the promote lookup key) and `testing-<YYYYMMDD>-<short sha>`; pushes to `main`, the weekly schedule and manual runs on `main` publish `latest` and `latest-<YYYYMMDD>-<short sha>`. The tags of one build share ONE manifest digest: `.github/scripts/push-tags.sh` (copied from octarine-os, tested by `tests/push-tags.sh` with stub podman and skopeo) pushes the first tag with `podman push --digestfile` and copies the others in the registry with `skopeo copy --all --preserve-digests`, reading every digest back and failing on a mismatch. Before 2026-11-13 the build pushed the image once per tag (a digest per tag, found while converting to GitLab Flow; it was never observed on a real run here, the same pattern was on octarine-os, where it kept a promotion from matching). The `sign` job (environment `signing`) signs the digest the push step outputs and verifies the digest and every tag against `cosign.pub`.
- Registry read-after-write (2026-11-17, found on the first main run after #36): GHCR answers `manifest unknown` or `no signatures found` for a short while after a push, copy or signing. Every read of something the same run just wrote goes through `.github/scripts/retry.sh <command>` (RETRY_TRIES 8, RETRY_DELAY 8: about a minute; the last attempt's status is the command's): the promote read-back of `latest` and the dated tag (the digest comparison happens after the read, so a real mismatch still fails at once), the `push-tags.sh` read-backs, the cosign verify before retagging and the three verifies of the sign job. Reads of old data (the testing tag the promote starts from, `promote-decision.sh`, `bins-pins.sh`) are not retried. Tests: `tests/retry.sh`, and `tests/push-tags.sh` with a stub registry that fails the first read of every tag. Evidence from run 44020428027 (attempt 1): the promote read-back failed with `manifest unknown` right after its first `skopeo copy`; in the datastore sign job the digest verified and the verify of the tag `latest` a second later said `no signatures found` although `push-tags.sh` had read back the same digest for that tag, so it was the same lag (the attempt-2 re-run passed unchanged); the tag read of the sign job cannot be proven to be lag from the log alone.
- Required check names in `build.yml`: the aggregate jobs `Build and push image` and `Sign and verify images` (each passes when every planned image succeeded or the plan was empty; signing runs inside the per-image workflow, so a failure anywhere fails both). Per-image jobs are shown as `images (<name>) / Build image` and `images (<name>) / Sign and verify image` and are not required.
- Pruning: old package versions are not pruned; public GHCR storage is free; delete old versions by hand in the GitHub packages UI if ever needed.
- Signing: public key `cosign.pub` is committed at the repo root. The private key is the secret `SIGNING_SECRET` stored in the GitHub environment `signing` (not at repo level, environment limited to `main` and `testing`); only the `sign` job uses that environment, so the build job never sees the key. `cosign.key` is gitignored and must never be read, printed or committed. Old bundle format (`--new-bundle-format=false --use-signing-config=false`). One-time setup (done 2026-11-07): `COSIGN_PASSWORD="" cosign generate-key-pair` (unprotected key, CI cannot use a passphrase), commit `cosign.pub`, store `cosign.key` as the environment secret `SIGNING_SECRET`, enable GitHub Actions. A new image's ghcr package is private after its first publish: Kevin sets it public in the web UI (not possible via API) so distrobox can pull it without login.
- Renovate and branch protection: automerge of base-digest bumps only works if protection on `main` lets it through; Renovate's own branches fail `require-testing-branch`, so those digest PRs need a manual merge or a ruleset exception (assumption, unverified until a Renovate PR exists; the Renovate app must be installed).
- Base digest pinning: Renovate (`config:best-practices`, Containerfile manager matching every `*/Containerfile`) pins the `FROM` digest of `ghcr.io/ublue-os/**` bases and opens update PRs; digest bumps of the base automerge. Actions are pinned by SHA and updated by Renovate and Dependabot.
- Commits: on the dev branch, explicit paths only (never `git add -A`), message says why, no `Co-Authored-By` trailer (Kevin, 2026-11-08).

## Deliberately not in the images

SDKMAN, nvm, Node, Java (runtime installs into the shared home); anything in `/home`; Terra or other repos beyond the base's; `ffmpeg-free-devel`; any OS-image tooling (bootc, rpm-ostree, kernel, bootloader, ISO/disk builders).
